Тестовите го покриваат увозот на рецепт преку URL во Mealie и се поделени
во два блока:
  Блок 2 (TEST 6–14)  — Дијалогот за парсирање на состојки, прикажан
                          веднаш по успешното скрепирање на рецептот.
  Блок 3 (TEST 15, 17, 20, 23) — Страната со рецепт во view режим откако
                          дијалогот е затворен.

Надворешна зависност:
  Рецептот се скрепира ЕДНАШ (во beforeAll на Блок 2) од:
    https://preppykitchen.com/molten-chocolate-cake/
  Потребна е интернет конекција. Скрепирањето + NLP парсирањето може
  да трае до 90 секунди, затоа beforeAll има timeout од 120 секунди.

================================================================================
АРХИТЕКТУРА — Скрепирај еднаш, повтори многупати
================================================================================

  Клучниот дизајн е дека скрепирањето се случува САМО ЕДНАШ во
  beforeAll на Блок 2. Резултирачкиот slug (пр. "molten-chocolate-cake")
  се зачувува во модул-нивото `sharedSlug` и се споделува со сите тестови.

  Зошто ова е важно:
    Ако секој тест скрепираше свое URL, тоа би значело 13 надворешни
    мрежни барања × до 90 секунди = потенцијално 20 минути само за
    скрепирање. Со sharedSlug, секој beforeEach само навигира на
    /g/home/r/{sharedSlug}?parse=true — нема ново скрепирање.

  Блок 2 beforeAll:
    1. Отвора привремен browser context (изолиран од тест-контекстите).
    2. Го брише "bittersweet chocolate" (cleanup-first).
    3. Навигира на /g/home/r/create/url, внесува URL, поднесува форма.
    4. Чека дијалогот "Ingredient Parser" да се отвори (до 90 секунди).
    5. Го извлекува slug-от од URL-то со regex и го зачувува во sharedSlug.
    6. Го затвора привремениот контекст.

  Блок 2 beforeEach:
    • Го брише "bittersweet chocolate" (осигурува дека храната е отсутна
      пред секој тест за да се прикаже "Create missing food" копчето).
    • Логирање.
    • Навигација на /g/home/r/{sharedSlug}?parse=true → дијалогот се
      отвора автоматски (Mealie го чита ?parse=true при монтирање).

  Блок 2 afterEach:
    • Го брише "bittersweet chocolate" (го чисти она што TEST 11 создава).

  Блок 2 afterAll: (нема — Блок 3 е сопственик на бришењето на рецептот)

  Блок 3 beforeEach:
    • Логирање.
    • Навигација на /g/home/r/{sharedSlug} БЕЗ ?parse=true → view режим,
      без дијалог.

  Блок 3 afterAll:
    • Го брише рецептот (DELETE /api/recipes/{sharedSlug}).
    • Го брише "bittersweet chocolate" (конечно чистење).
    • Блок 3 — не Блок 2 — е сопственик на бришењето за да нема
      состојба на трка каде рецептот би се избришал пред Блок 3 да
      заврши.

ВАЖНИ ТЕХНИЧКИ ЗАБЕЛЕШКИ
================================================================================

  • Зошто getByRole('textbox', { name: 'Recipe URL' }) наместо getByLabel:
    Vuetify v-text-field рендерира и input елемент и копче "Clear Recipe URL"
    (икона ×). И двата го имаат достапното ime "Recipe URL", па getByLabel
    би наишло на strict mode violation (2 елементи). getByRole('textbox')
    ја стеснува претрагата само на input елементот.

  • Зошто waitForURL(/recipe_import_url=/) пред Enter:
    Формата чита recipeUrl од route.query (не директно од v-model). Кога
    корисникот типка во полето, Vue вика router.replace() асинхроно за да
    го запише вредноста во query string-от. Ако Enter се притисне пред
    router.replace() да заврши, route.query е сè уште null и createByUrl()
    излегува без да го повика API-то. waitForURL(/recipe_import_url=/)
    гарантира дека query string-от е populated пред поднесувањето.

  • Зошто page.mouse.click(10, 10) за TEST 13:
    Vuetify-евиот v-overlay компонент слуша на @click:outside настан.
    Тој настан се активира само при вистински pointer-down настан надвор
    од картата на дијалогот. Координатите (10, 10) — горниот лев агол на
    viewport-от — гарантирано се надвор од центрираниот дијалог без разлика
    на неговата големина.

  • Зошто .first() за текстови во Блок 3:
    Mealie ги рендерира некои елементи двапати во DOM-от (за различни
    layout breakpoints — mobile и desktop) користејќи CSS за прикажување.
    getByText() без .first() би наишло на strict mode violation (2 елементи).
    .first() потврдува дека барем еден од дупликатите е видлив.

  • Управување со "bittersweet chocolate":
    Оваа храна НЕ е во стандардната база на Mealie. NLP парсерот ја открива
    во состојките, но не може да ја поврзе со позната храна → food-error = true.
    Тоа е состојбата потребна за TEST 8, 10 и 11. beforeEach ја брише пред
    секој тест; afterEach ја брише по секој тест (за TEST 11 кој ја создава).

TEST 10 — Дали копчето "+ Create missing food" е видливо кога храната
           не е препознаена?
────────────────────────────────────────────────────────────────────────────────

  Копчето се прикажува само кога се исполнети ДВА услова:

  Двата услова се исполнети бидејќи "bittersweet chocolate" е избришана.

  Тестираме дали:
    • Копчето со текст /create missing food/i е видливо ✓

  ОЧЕКУВАН РЕЗУЛТАТ: Тестот ПОМИНУВА.

TEST 11 — Дали кликањето "+ Create missing food" ја создава храната и
           го крие копчето?
────────────────────────────────────────────────────────────────────────────────

  Кликаме на копчето. Тоа праќа POST /api/foods и ја поврзува новата храна
  со тековната состојка (food.id е сет). Вториот услов за прикажување на
  копчето (food?.id е falsy) станува false → копчето исчезнува.

  Тестираме дали:
    • Копчето со текст /create missing food/i повеќе НЕ е видливо ✓
      (timeout 5 s за асинхроното API барање)

  afterEach ја брише создадената храна за следниот тест.

  ОЧЕКУВАН РЕЗУЛТАТ: Тестот ПОМИНУВА.

TEST 17 — Дали картонот со информации ги прикажува Total Time, Prep Time,
           Cook Time и Serves X?
────────────────────────────────────────────────────────────────────────────────

  Овие вредности се скрепираат од schema.org/Recipe метаподатоци на
  страната (prepTime, cookTime, totalTime, recipeYield).

  Mealie ги рендерира информациите двапати во DOM-от (за различни layout
  breakpoints — mobile и desktop). Затоа се користи .first() за да се
  избегне strict mode violation при getByText().

  Тестираме дали:
    • "Total Time" (first()) е видлив ✓
    • "Prep Time" (first()) е видлив ✓
    • "Cook Time" (first()) е видлив ✓
    • /serves \d+/i (first()) е видлив (пр. "Serves 4" или "Serves 12") ✓

  ОЧЕКУВАН РЕЗУЛТАТ: Тестот ПОМИНУВА.

TEST 20 — Дали секцијата Ingredients прикажува наслов и барем една состојка?
────────────────────────────────────────────────────────────────────────────────

  Рецептот за Molten Chocolate Cake содржи масло, чоколадо, јајца, шеќер
  и брашно. Regex-от /butter|chocolate|egg|sugar|flour/i ги покрива сите
  и е отпорен на мали промени во текстот помеѓу скрепирањата.
  .first() се користи поради двојниот layout рендеринг.

  Тестираме дали:
    • getByRole('heading', { name: 'Ingredients' }) е видлив ✓
    • Барем еден елемент со текст /butter|chocolate|egg|sugar|flour/i
      (first()) е видлив ✓

  ОЧЕКУВАН РЕЗУЛТАТ: Тестот ПОМИНУВА.
